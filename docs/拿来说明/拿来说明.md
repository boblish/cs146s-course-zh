# 拿来说明

> 要求：写清「我拿走了什么 + 下次怎么用」。以下 5 条都来自这次 C1 的真实过程，每条都指向一个**可以搬到别的任务上的具体做法**，不是对挑战要求的复述。
>
> **发布仓库**：<https://github.com/boblish/cs146s-course-zh>（管线 + 术语表 + 中文译稿 + 四份交付物，不含课程原文）

## 1. 网页正文抽取：先做「样板行体检」，再谈翻译

- **我拿走了什么**：网页抽成正文时，页脚和导航会被当成正文混进来。判断标准是问一句「这一行脱离原页面还有意义吗」——`© 2026 Stytch`、孤零零的 `### Follow` 显然没有。而这类样板的根因往往是抽取器只按语义标签（`<footer>`）跳噪音，实际上页脚被写在普通 `<div>` 里。
- **下次怎么用**：任何抓取语料的任务，都先跑一遍样板行体检——段长分布 + 版权/栏目名正则扫描，先清洗再开工。这份黑名单规则可以跨站复用，比每次手工删要可靠得多。

## 2. 长任务要设计成「可断点续跑 + 按内容指纹去重」

- **我拿走了什么**：翻译进度不按「第几批已交」记，而按每段文本的指纹记。重复提交不会重复计数，漏掉的段落下次导出时自动重新出现，中途中断、合并批次、重译某几段都不会把进度写坏。
- **下次怎么用**：凡是需要多轮人工参与的批处理——翻译、标注、校对、数据清洗——都用「内容指纹 + 幂等回填」这套结构，替代手工维护的进度表。这是这次最值得直接搬走的一块骨架。

## 3. 指标口径错了，比功能坏了更危险

- **我拿走了什么**：导出报 97 段、实际数出 107 个标记，第一反应是「丢数据了」。真相是批文件抬头自带 2 处示例标记，差额恰好等于 2 × 批数。还有一次是拿重分段之前的旧覆盖度当现状，读数虚高十倍以上。
- **下次怎么用**：对不上账时，先怀疑口径（统计脚本把示例、注释、抬头算进去了吗？这份报表是哪一版数据算的？），再怀疑实现；对账结果要能解释成精确的数学关系，而不是「大概差不多」。

## 4. 术语表是翻译质量的单点控制，值得在开工前一次性对齐

- **我拿走了什么**：译文的可读性差异主要来自术语是否统一，而不是提示词写得多漂亮。把 `Vibe Coding → 氛围编程`、`Agent → 智能体`、`Agentic AI → 智能体式 AI` 这类对应关系连同「哪些保留英文」「缩写首次出现给全称」一起定死之后，译文的连贯感立刻稳定下来。
- **下次怎么用**：换领域时只改术语表这一个文件，管线其余部分完全不动。术语表至少要包含四列：原词、中文译法、是否保留英文、使用说明（含首现写法）。

## 5. 源头拿不到时，「如实标注」比「硬凑」更专业

- **我拿走了什么**：37 份源资料里，有付费墙、反爬失败、纯脚本渲染、图片型 PDF 拿不到正文的情况。之前我会觉得「缺了就是不完整」，这次选择写进 README 的「已知缺口」表，逐条写清现象与已尝试的途径。
- **下次怎么用**：任何以「覆盖度」为指标的任务，交付前做一次来源可用性对账表：总数、可得、部分可得、不可得，不可得的单列并说明原因。这样读者能判断哪些结论有证据支撑、哪些是资料本身的空白。

## 6.（附）对 AI 的使用方式：把裁决留在自己手里，把批处理交出去

- **我拿走了什么**：AI 在批处理和诊断上极强（定位到页脚根因、对账 97 与 107 的差额），但它不会替你定义「什么算正文」「什么算译完」；它还会把陈旧的汇总数字当成现状报给你。
- **下次怎么用**：分成两层——判据、取舍、是否如实标注由人拍板，并立刻固化进配置文件；规则明确、可校验的执行全部交给 AI，且要求它「先给判据再给结果」，汇总数字必须先说明口径与生成时间。
